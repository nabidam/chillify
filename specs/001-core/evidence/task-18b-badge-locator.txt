hand-edited..." entry, as findings not fixed by that task, and in
specs/001-core/evidence/task-18a-slider-a11y.txt section 4):

1. color-contrast (serious): destructive Badge variant renders #ffffff on

   playlist context" test fails before its own axe assertion ever runs.

1. Fixes applied
======================================================================

- frontend/src/components/ui/badge.tsx: the `destructive` variant's
  `text-white` (a raw, non-token color) is now `text-destructive-foreground`,
  matching DESIGN.md's confirmed pairing (destructive-foreground on
  destructive = 7.23:1) and the tokens already present in
  frontend/src/styles/tokens.css. The other four Badge variants already used
  token-based foreground classes and were left unchanged. Button's identical
  `text-white` pattern on its own destructive variant is a different
  component, out of this fix's scope, and untouched.
- frontend/tests/e2e/accessibility.spec.ts: the "an empty playlist context"
  test's `create` locator now ends in `.first()`, with a comment explaining
  the deliberate two-button duplicate (header action + empty-state CTA, both
  named "Create Playlist" per UX.md's S9 section) and pointing at the
  identical, already-established disambiguation in gate-3.spec.ts and
  firefox-smoke.spec.ts.
- ARCHITECTURE.md: new 2026-07-26 decision-log entry recording both fixes
  and the defect-2 diagnosis (true, intentional duplicate — not fixed by
  renaming either button, not a markup bug).

Defect-2 diagnosis: TRUE DUPLICATE, both renders correct per UX.md. UX.md's
S9 section specifies exactly one primary action, "Create Playlist," and
names it from two places: the header ("survives every state") and the
empty-state card ("offer Create Playlist"). Both buttons open the identical
PlaylistEditorDialog in create mode — there is no second, distinct action to
give a different name. The rest of the e2e suite already treats this as
intentional: gate-3.spec.ts and firefox-smoke.spec.ts both already narrow
with `.first()` (gate-3.spec.ts has its own comment: "The empty playlists
screen shows a Create Playlist button in both the header and the empty-state
card; the header one is always present"), and screen-states.test.tsx's
component-level equivalent seeds a non-empty list specifically so only the
header button exists and the collision never has to be resolved there.
accessibility.spec.ts was simply the one file in this family not yet
brought in line with that established pattern. Per this task's own
instruction ("Only if both are legitimately identical and correct should
the test locator be narrowed"), the fix is exactly that narrowing — not a
markup change, and not a UX.md-violating rename of either button.
